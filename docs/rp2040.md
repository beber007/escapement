# The Raspberry Pi RP2040 port

**In short.** On a Pico, the hard, the soft and the power-aware kernel run, the last
under its four policies with the DVFS driver moving between 12, 50 and 125 MHz; so do
the timer events, the UART and the 4-slot buffer between the two cores. A scheduling
round costs 3.2 µs under the hard kernel, 0.33 % of the processor at one round a
millisecond; the periods read +28 ppm on a frequency counter, the crystal's tolerance;
timer events are delivered on the microsecond; a change of speed takes 4 to 9 µs; the
4-slot buffer carried 326,525 reads between the cores without a torn one. Not measured
yet: current and energy, which decide whether DVFS is worth anything. The 2^30 wrap of
the kernel clock, and the core undervolted under the kernel, have run under emulation
only.

The Raspberry Pi Pico port lives in `Escapement/CORTEX-Mx/RP2040/` and comes to
**1,615 lines** on 2026-09-25, headers and linker script included (1,245 on
2026-09-22, before the launch of core 1 and the trace), against 4,375 for the STM32
layer — the latter spends 1,757 lines on its per-derivative vector tables alone, where
the RP2040 has a single part and 26 interrupts.

| File | Role | Lines |
|---|---|---:|
| `Escapement_Timer.c` | the five functions the kernel expects, on TIMER | 305 |
| `Escapement_TimerEvent.c` | event manager on a free alarm, for event-driven tasks | 215 |
| `Escapement_UART.c` | PL011 driver, transmission through a queue of buffers | 241 |
| `Escapement_Processor.c` | clock tree: crystal, PLL, derived clocks; DVFS driver | 265 |
| `Escapement_Interrupts.c` | vector table and dispatch of the 26 IRQs | 102 |
| `Escapement_Core1.c` | launch of core 1 | 76 |
| `RP2040_SRAM.ld` | linker script | 66 |
| `Escapement_RamEntry.S` | entry stub for a firmware loaded into SRAM | 32 |
| headers | | 313 |

## Two design choices

**The firmware executes from SRAM.** The RP2040 normally boots from an external
QSPI flash, which requires a 256-byte second-stage bootloader with its CRC.
Linking into SRAM avoids it — this is what the `no_flash` build type of the SDK
does — and takes the flash out of the power measurement, which will serve the
power-aware variant. The application points `VTOR` at `0x20000000` before
enabling interrupts.

**Time is rebuilt modulo 2³⁰.** The RP2040 counter is a free-running 64-bit one
that never wraps in practice, whereas Escapement expects a counter that wraps at
2³⁰ and signals every wrap. `ALARM0` carries the deadline set by `_OSSetTimer`,
and `ALARM1`, rearmed on each 2³⁰ boundary, plays the part of the overflow
interrupt.

Above all, **the timer is fed by a 1 µs tick derived from `clk_ref`, independent
of `clk_sys`**: changing the core frequency does not move the time base of the
kernel. On the STM32, the timer clock follows the core clock, which complicates
DVFS.

## Execution on real hardware

The port has been **validated on a Raspberry Pi Pico W**, loaded into SRAM over
SWD with the official Debug Probe — no BOOTSEL button needed:

```sh
openocd -f interface/cmsis-dap.cfg -c 'adapter speed 5000' -f target/rp2040.cfg \
        -c 'init; reset halt; load_image build/UARTEchoPico.elf; resume 0x20000000; exit'
```

`UARTEchoPico` sends back every byte received on UART0 (GP0 and GP1, 115200
baud):

```
sent b'escapement'  -> received b'escapement'   ECHO OK
sent b'RP2040 ok'   -> received b'RP2040 ok'    ECHO OK
sent b'0123456789'  -> received b'0123456789'   ECHO OK
```

And `TaskLEDPico`, inspected over SWD while it was running:

```
PC       = 0x20000864     the wfi of IdleTask
timer    advances by 136,241 µs between two reads
alarm0   armed 1,620 µs ahead of the counter
gpio_out = 0x8            GP3 high, a task was executing
```

The scheduler does arm its deadlines in the future.

> On a **Pico W**, the on-board LED is not on GP25: it is driven by the CYW43439
> wireless chip, and GP25 serves as the chip select for that chip.
> `TaskLEDPico` nevertheless declares it as its first output — on a Pico W, look
> at GP2 and GP3 with a scope, or go through the UART.

## Kernel time needs an origin

The RP2040 counter runs freely from power-up and is never reset, whereas
Escapement assumes its clock starts near zero. On a board that has been powered
for a few hours the counter exceeds a billion microseconds: the kernel believed
itself instantly late on every deadline and fell onto its overload guard.

`_OSStartTimer` therefore captures the instant it starts, and every kernel time
is counted from that origin. **This defect was only visible on hardware**: the
counter of the emulator always starts at zero.

## The core runs at 125 MHz

`OSInitializeSystemClocks` engages the PLL, because the per-activation cost of
the kernel sets a floor on the achievable period. The power-aware kernel then
moves between 12, 50 and 125 MHz, see `power-aware.md`. The reference and peripheral
clocks, on the other hand, **stay on the crystal**: the first keeps the
one-microsecond tick exact whatever the core does — which is what makes this
chip a good target for the power-aware variant — and the second lets the UART
divide a frequency the driver knows.

## Cost of one scheduling round

Measured on the board, from the hardware timer interrupt to the rearming of the
next deadline — which covers the interrupt, the software handler, the transfer
of arrivals into the ready queue and the election of the next task. Task set of
four: 1, 10, 20 and 60 ms, whose arrivals all fall on the millisecond, hence one
round per millisecond. Remeasured on 2026-09-23, about 10 s per build, at `-O2`:

| | Rounds (about 10 s) | Mean | Maximum | Share of the processor |
|---|---:|---:|---:|---:|
| Hard, earliest-deadline-first (as shipped) | 10,061 | **3.2 µs** | **8 µs** | **0.33 %** |
| Hard, deadline-monotonic | 10,060 | 3.2 µs | 8 µs | 0.33 % |
| Soft | 10,061 | 4.4 µs | 13 µs | 0.44 % |
| Power-aware | 10,060 | 4.2 µs | 9 µs | 0.43 % |

Some 400 cycles per round at 125 MHz for the hard kernel, whichever the
scheduling algorithm: ordering the ready queue by deadline costs nothing
measurable on four tasks. At `-O0` the hard kernel took 7.0 µs on average and
26 µs at worst, so these numbers say as much about the build as about the design.
The soft kernel could not be built for the Pico until 2026-09-22: `TaskLEDPico` lacked
its branch, and the `Makefile` never linked `EscapementSoft.o`.

`tools/measure_cost.sh` counts the rounds from the load to the reading, a little over
10 s, whose length depends on the machine that drives the probe (`tools/board_ci.sh`):
the board checks have read 10,067, 10,135 and 10,255. The share of the processor divides
the summed cost by 10 s, and runs high by the same margin.

The first publication gave 3.2 and 8 µs as well, but 13,409 rounds in 10 s and
0.43 % of the processor. Rebuilt from the very revision that published them
(7c84eca, with only the later fix of the pending timer interrupt, without which
it no longer starts after a load), the same image now counts 10,061 rounds: the
cost per round reproduces, the count of rounds did not, and why was not established.

The power-aware kernel always runs its rounds at 125 MHz: its idle task sleeps at
full speed (see below), so the alarm finds the core there, and the round lowers
the speed only once the next deadline is armed. The trace of that build, whose
points add about a microsecond, gives 5.3 µs on average and 11 µs at worst over
276 rounds, all begun at 125 MHz.

The instrumentation lives in `Escapement_Timer.c` under
`ESCAPEMENT_MEASURE_SCHEDULING_COST`, and is **off in the example as shipped**:
it adds work to the critical path it measures, and it changes how the board
behaves under a debugger. To reproduce the figures, uncomment it in
`Escapement_Config.h`, rebuild, and run `tools/measure_cost.sh`, which refuses to
run against a binary that carries no counters.

The second effect is that of `TIMER_DBGPAUSE`, which the measurement build clears:
see “The timer and the debugger” below.

One more trap, on the reading side: the counters must be read one symbol at a
time. The linker reorders them between optimisation levels, so reading four
consecutive words returns whatever happens to sit there — in our case
neighbouring pointers, presented as microseconds.

## Confirmed by an independent instrument

The three outputs were measured with the frequency counter of a Bus Pirate v4,
connected to `AUX` and a common ground:

| Output | Task | Expected | Measured | Deviation |
|---|---|---:|---:|---:|
| `GP4` | 1 ms, toggles on every instance | 500.000 Hz | **500.02 Hz** | +40 ppm |
| `GP2` | 20 ms, pulse | 50.0000 Hz | **50.0014 Hz** | +28 ppm |
| `GP3` | 60 ms, pulse of varying width | 16.66667 Hz | **16.66713 Hz** | +28 ppm |

Eight consecutive readings on `GP3` give the same value to within one part in a
hundred thousand. The +28 ppm deviation, **identical on the two most precise
measurements**, is not noise: it is the tolerance of the crystal on the board
relative to the reference of the instrument, squarely within the usual ±30 ppm.

This is the one measurement in the project that depends **neither on the kernel,
nor on the emulator, nor on the debugger**. A second device confirms the three
scheduling periods, including that of the task whose execution time varies from
one instance to the next — its period does not.

## The timer and the debugger

The RP2040 freezes its counter as soon as a core is halted by the debugger
(`TIMER_DBGPAUSE`). The port **keeps that behaviour in the shipped build and turns it
off in the measurement build** (`ESCAPEMENT_MEASURE_SCHEDULING_COST`), each for a
reason given in `_OSStartTimer`.

Kept, it stops time whenever the debugger stops a core, which stepping through a
real-time kernel requires. Without it, the kernel clock ran on through the halts that
loading over SWD imposes — reset, image transfer, restart of the second core, several
tens of milliseconds in all — and through every inspection, while the tasks did not.
A task of 10 ms or more absorbs that; a task of 1 ms is twenty periods late, and the
catch-up loop makes it arrive again before it has had a chance to run: the overload
guard fires, rightly so. The state captured when it fired said as much, with three
tasks late by 18 to 26 ms at the same instant — exactly the duration of the loading
sequence. Finding that took a long investigation.

Turned off, it lets a running board be watched. The probe halts both cores and never
resumes core 1, since resuming it from wherever the bootrom left it restarts the chip,
so with the pause kept a single SWD inspection freezes the kernel clock for good: an
alarm of the RP2040 fires on equality, and a deadline the counter has passed once it
resumes is never reached again. The board keeps executing and its outputs still move,
but no deadline comes. Reading the cost counters or the trace therefore takes the
measurement build.

## Two pitfalls met along the way

**Reloading without resetting.** Loading a firmware over SWD on top of another
leaves the peripherals in the state the previous one left them. The timer stayed
armed, its interrupt fired, and `_OSIOHandler` found no descriptor: it went into
its trap with interrupts disabled. Hence the `reset halt` before `load_image`.

**Priming the transmission.** On the USART of an STM32, `TXE` reflects a state:
arming the interrupt fires it immediately. On the PL011 of the RP2040 it fires
on a FIFO threshold being crossed — arming it while the FIFO is already empty
produces nothing. `OSEnqueueUART` has to write the first bytes itself to prime
the transmission.

## The power-aware kernel on the board, through a trace

Watching a running board from the debugger turned out to disturb what it watched,
three ways:

- loading an image stops both cores and resumes core 0 only, and the timer, set by
  the port to pause while a core is stopped by the debugger, stays frozen;
- stopping core 0 to read its registers lets time run on while the tasks do not: the
  1 ms probe misses its deadline and the kernel stops on its overload guard — which
  was first taken for a defect of the kernel;
- each read of memory over SWD takes about a millisecond, so a series of them is no
  snapshot.

Hence a trace (`Escapement/CORTEX-Mx/Escapement_Trace.h`, `make TRACE=1`): the
port writes the events of the scheduling, with the time of the timer, into a ring
buffer of 256 entries, and `tools/read_trace.py` suspends the recording, reads the
buffer in one transfer and lets it go on, without stopping a core. Built with
`ESCAPEMENT_MEASURE_SCHEDULING_COST` as well, so that the kernel frees the timer
itself, the image runs untouched from the load on.

The hard kernel, one round of every millisecond:

```
 40000 us  alarm0
 40001 us  soft>                       software timer handler entered
 40005 us  set_timer ahead 996 us      next deadline armed
 40006 us  soft<
 40007 us  mark gpio 4 start           the probe task runs
```

The power-aware kernel, whose first image stalled at once — the trace showed the
alarm and the handler entered, then nothing. The timer, which a reset of the
processors alone does not reset, still had the alarm of the previous image armed;
the NVIC kept its interrupt pending although it was not yet enabled, and took it as
soon as it was, before the idle task had set the origin of time. The port now
clears that pending state. With it, the DVFS driver works on the silicon:

```
 31999 us  alarm0
 32000 us  soft>
 32004 us  set_timer ahead 995 us
 32007 us  speed 125 MHz -> 12 MHz     slowed down for the probe
 32016 us  soft<                        9 us: the handler, now at 12 MHz
 32029 us  mark gpio 4 start
 32047 us  speed 12 MHz -> 125 MHz     back to full speed in the idle task
```

The 50 MHz point is taken too, for the other tasks; the figure in the
README draws such a trace, `tools/read_trace.py --csv` feeding
`tools/dvfs_figure.py`. One thing the trace makes
plain: the idle task goes back to 125 MHz before it sleeps (`_OSSleep` of the
power-aware kernel), so the core spends nearly all its time asleep with the PLL at
full speed. Whether that costs anything is for the current bench to say.

### The other power-management policies

`make KERNEL=PA POWER=DRA`, `DR_OTE` or `DM_SLACK` builds `TaskLEDPico` under the
three policies other than OTE. Run on the board on 2026-09-24, each with the trace
and then with the cost counters of the section above (about 10 s per build, at `-O2`):

| Policy | Speed changes in 6 × 256 events | Rounds (about 10 s) | Mean | Maximum | Share |
|---|---|---:|---:|---:|---:|
| OTE (default) | 12 ↔ 125 MHz about 190 times each way, 125 ↔ 50 MHz 18 | 10,058 | 4.2 µs | 9 µs | 0.43 % |
| DRA | none | 10,058 | 7.4 µs | 15 µs | 0.74 % |
| DR_OTE | as OTE | 10,058 | 6.5 µs | 14 µs | 0.65 % |
| DM_SLACK | as OTE | 10,059 | 4.2 µs | 9 µs | 0.43 % |

Every task keeps its period under all four: the probe every 1000 µs within
±20 µs, the jitter of the rounds at 12 MHz, and the 10 and 20 ms tasks within
±6 µs. DRA never changes speed, as under Renode: it hands a task only the time
left by instances of earlier deadline that have ended, and in this task set none
is left. DR_OTE and DM_SLACK pick the same speeds as OTE, which DM_SLACK had
already done in every run on the host before `reclaim`.
The price is in the round: DRA and DR_OTE keep a second queue, a simulation of the
schedule at the worst-case execution times, which every arrival and every
completion updates, and a round costs them 2 to 3 µs more; DM_SLACK costs what OTE
costs.
OTE, remeasured on the images these changes produced, gives the 4.2 µs and 9 µs of
2026-09-23 again, and 5.3 µs and 11 µs through the trace.

## Timer events on the board

`TestTimerEventPico` leaves a mark in the trace when each of its tasks raises or
lowers its output, and the event manager one when it delivers an event, with how
late the alarm fired; `tools/read_trace.py --pins` sums the marks up per output, and
`tools/timer_events.py` loads the image and sums up several readings, as the checks
on the board do. Two defects of the port stood in the way on 2026-09-22: the vector
table sent alarms 2 and 3 to the handler of undefined interrupts, and the port wrote
`INTE` and `INTF` whole, which would have cleared the bits of another alarm; it now
goes through the atomic set and clear aliases.
Five seconds of each kernel on 2026-09-23:

| Kernel | GPIO 2: period, high | GPIO 3: period, high |
|---|---|---|
| Hard | 4999–5001 µs, 1012 µs | 10000 µs, 2012 µs |
| Soft | 4998–5002 µs, 1011–1012 µs | 10000 µs, 2012 µs |
| Power-aware | 4999–5001 µs, 1012–1013 µs | 10000 µs, 2013 µs |

Every event was delivered on the microsecond its alarm was set for. The 12 µs over
the requested 1000 and 2000 are the path from the alarm to the event-driven task:
the interrupt, the software timer handler, the switch of context. The power-aware
kernel changed no speed: event-driven tasks keep it at full speed by design.

The frequency counter of the Bus Pirate, on `GP3`, read 100.0031 Hz eight times in a row
under each of the three kernels, against 100 Hz expected: +31 ppm, against the +28 read
on 2026-09-20 — the crystal of the board again, a few ppm apart, and the same to the
last digit whichever kernel schedules the task and the event that shape the output.

## Where the idle task sleeps

The power-aware kernel lets its idle task sleep at 125 MHz: `_OSSleep` raises the speed
before each `WFI`, and the core spends nearly all its time there. `make KERNEL=PA
SLEEP_SPEED=n` chooses another operating point (0 for 12 MHz, 1 for 50 MHz); the default
is unchanged, and so are its images. Sleeping slower, the idle task raises a flag before
its `WFI`, and the interrupt that wakes it raises the speed to the maximum as it enters
(`_OSIOHandler`). Only the idle task is sped up that way: the kernel counts the work of
an interrupted task at the speed it ran at, and a task running at 50 MHz must not be
counted at 125.

Measured on the board on 2026-09-23, `TaskLEDPico` and `TestTimerEventPico`, the cost of
a round with the counters of `measure_cost.sh` — which start once the speed is up — the
rest from the trace:

| Idle sleeps at | Cost of a round | Alarm to probe | High time of the 1 ms event | Event late by |
|---|---:|---:|---:|---:|
| 125 MHz (default) | 4.2 µs | 30 µs | 1012 µs | 0 µs |
| 12 MHz, speed raised by the kernel's handler | 21.3 µs | 57 µs | 1084 µs | 7 µs |
| 12 MHz, speed raised as the interrupt enters | 4.2 µs | 46 µs | 1028 µs | 16 µs |
| 12 MHz, the same through `_OSRaiseSpeedOnWake` | 4.2 µs | 42 µs | 1025 µs | 13 µs |
| 50 MHz, speed raised as the interrupt enters | 4.2 µs | | 1019 µs | 7 µs |

Every deadline holds and the periods do not move — the delay is the same at every
round. Raised by the kernel's handler, the speed came up only after the entry of the
interrupt, the alarm handler, the switch to the software timer and the first part of the
kernel had all run at 12 MHz; raised as the interrupt enters, what runs slow is the
entry itself, some 7 µs, and then the change of speed, some 9 µs from 12 to 125 MHz —
more than a switch of clock source should take, the PLL staying locked. Whether sleeping
at 12 MHz saves more than those microseconds cost is for the current bench to say.

`BenchDVFSPico.c` (`make KERNEL=PA bench`) times the changes of speed alone, without the
kernel, 10,000 times each, from the 1 µs counter of the timer. At 12 MHz the core and the
counter run off the same crystal, so that a loop of fixed length would meet the counter
at the same phase every time and the mean would stay a whole number of microseconds; a
pseudo-random wait before each measurement breaks that; `tools/dvfs_bench.py` loads it
and prints the means. The means below, of 2026-09-24, most likely include the two
reads of the counter that bracket each change: rebuilt later that day with another
compiler, on the Mac mini, the bench gave 8.83 µs from 12 to 125 MHz with the reads and
8.16 µs without, the two reads costing 0.5 to 0.7 µs at 12 MHz and 0.06 µs at 125:

| Change of speed | Time |
|---|---:|
| 12 → 125 MHz | 8.7 µs |
| 12 → 50 MHz | 7.9 µs |
| 50 → 125 MHz | 5.5 µs |
| 125 → 50 MHz | 5.1 µs |
| 125 → 12 MHz | 4.1 µs |
| 50 → 12 MHz | 3.9 µs |

Timed one by one at 12 MHz, the register accesses of 12 → 125 MHz add up to some
2.6 µs: writing `VREG` 0.4, parking `clk_sys` on the reference — where it already is —
1.0, the post-divider of the PLL 0.5, `clk_sys` onto the PLL and its acknowledgement 0.7.
No wait for the PLL or the regulator hides in there. The rest is the driver's own code,
run at 12 MHz, where each instruction takes 83 ns: saving and masking interrupts, the
tests of the voltage table, the calls.

The wake-up therefore has a path of its own, `_OSRaiseSpeedOnWake`, which `_OSIOHandler`
takes when the flag of the idle task is up: the tests the way up needs and no more, and
from 12 MHz no parking of `clk_sys` on the reference it is on. It tests and clears the
flag with interrupts masked, so that an interrupt of higher priority arriving meanwhile
raises the speed itself. It takes 6.0 µs from 12 MHz where `OSSetProcessorSpeed` took 8.7,
and 4.3 µs from 50 MHz instead of 5.5; the probe starts 42 µs after its alarm, the
event-driven task 13 µs late — the last row of the table above.

### The regulator

`BenchVregPico.c`, in the same target, times the core regulator. The chip's only witness
of its output is the `ROK` bit of `VREG`, which reports the output in regulation — about
90 % of the target by the usual reading — and does not drop for the step the driver
makes, 1.05 to 1.10 V. The bench therefore steps up from lower, the core at 12 MHz and the
brown-out detector lowered to 0.817 V, as `UNDERVOLT=1` does: below the 1.05 V the
datasheet guarantees, which the chip went through without a fault. 1,000 steps each, the
time until `ROK` is back, on 2026-09-24:

| Step | Low voltage held 500 µs first | Held 3 ms first |
|---|---:|---:|
| 0.90 → 1.10 V | 46.6 µs, 48 at most | 47.7 µs, 49 at most |
| 0.95 → 1.10 V | `ROK` never drops | 30.9 µs, 34 at most |
| 0.90 → 1.05 V | 26.3 µs, 27 at most | 26.5 µs, 27 at most |
| 1.00 → 1.10 V | `ROK` never drops | `ROK` never drops |
| 1.05 → 1.10 V | `ROK` never drops | `ROK` never drops |

Two readings. Rising, the regulator reports its output in regulation within 50 µs, so that
the 100 µs `RP2040_VREG_SETTLING_US` waits before raising the clock, undervolted, leaves a
margin of two; how long the last tenth takes, `ROK` cannot say. Falling, the output is
slow: with 500 µs at 0.95 V it had not come down far enough for `ROK` to drop on the way
back up, a linear regulator lightly loaded at 12 MHz having nothing but that load to pull
its output down. A lower voltage asked for is therefore not a lower voltage obtained,
not for hundreds of microseconds, which matters to what DVFS saves.

## The 4-slot buffer between the two cores

The kernel schedules on core 0 alone, and its lock-free mechanisms were checked on one
core, the writer an interrupt handler. Of the three, Simpson's four slots need no atomic
instruction at all, and were designed for a writer and a reader on processors of their
own: they should hold between the two cores of the RP2040 as they stand. The 3-slot
buffer and the FIFO queue should not — their LL/SC pair is emulated with a reservation
bit that interrupts clear and a store from the other core does not, and the announced
operation of the queue assumes preemptions that nest.

First the model: `test/model/fourslot.py` now also explores two cores, where the writer
runs beside the reader and publishes a slot in four steps, one per statement of
`OSWriteBuffer`, any of the reader's able to fall in between. The kernel's buffer holds;
a writer that publishes the pair before its slot, which one core cannot tell from the
kernel, is caught on two.

Then the board. `FourSlotCoresPico` starts core 1 (`OSLaunchCore1`,
`Escapement_Core1.c`: the handshake with the bootrom through the inter-core FIFO,
after a reset of core 1 through the power-on state machine, as the pico-sdk does).
Core 1, bare, writes records of eight words, all eight the same counter rising by one,
as fast as it can, into a 4-slot buffer and into a plain array; a task on core 0 reads
both 32 times each millisecond and counts the reads that mix two records and those that
go backwards. `tools/fourslot_cores.sh` loads it and reads the counts back while both
cores run. On 2026-09-24, 10 s each:

| Kernel | Records written | Reads of each | 4-slot: torn, backwards | Plain array: torn |
|---|---:|---:|---|---:|
| Hard, EDF | 1,260,703 | 321,760 | **0, 0** | 17,061 (5.3 %) |
| Hard, DM | 1,260,817 | 321,760 | **0, 0** | 17,192 |
| Soft | 1,261,074 | 321,792 | **0, 0** | 17,213 |
| Power-aware, reader every 1 ms | 1,260,782 | 321,760 | **0, 0** | 16,815 |
| Power-aware, reader every 2 ms | 1,047,620 | 160,896 | **0, 0** | 3,269 |

No read of the buffer mixed two records or went back to an older one; the plain array,
the same writer and the same reader without the mechanism, tore about one read in
twenty. A run of the reader took 314 µs at most, core 1 contending for the memory.
Told 400 µs every millisecond, the power-aware kernel had no lower speed to take and
stayed at 125 MHz (trace). Every 2 ms, as the example now runs under it, it takes the
reader down to 50 MHz and the idle task back to 125, 86 times each way in two readings
of the trace; core 1, on the same clock, writes through both — a sixth fewer records
than at 125 MHz throughout — and the buffer still gives neither a torn read nor one
going backwards.

These runs predate the memory barriers of 2026-09-25. Taken to cores that may perform
their loads and stores out of program order, as Armv6-M allows (A3.7), the model of
the buffer asks for four, which the kernels now have (`method.md`). The board had shown
no torn read without them; the architecture did not promise it. With them, the checks
on the board below read on 2026-09-25 (6f90fa2) 326,525 reads under the hard kernel and
163,424 under the power-aware one, none torn or going backwards. The plain array tore
3,428 and 1,675 times, about 1 %, where it had torn 5 % under the hard kernel and 2 %
under the power-aware one; why fewer is not established.

Three things stood in the way:

- **OpenOCD holds core 1.** By default it halts both cores and resumes core 0 alone.
  Core 1 held by the debugger cannot be started, and the timer, which pauses while
  either core is held, would stop the kernel too. The script tells OpenOCD to handle
  core 0 only (`set USE_CORE 0`), and never touches core 1.
- **A watchdog armed by the firmware in flash.** A reset of the processors leaves the
  watchdog running, and it pauses while the debugger holds either core. Core 1 had
  always been held until now; running, it let the watchdog fire within a second, and
  the chip rebooted into the flash (`WATCHDOG_REASON` = timer). The example disarms it.
- **Two loops in step.** Both cores run off the same clock and loop without end.
  Without a random wait before each read, 6528 reads of the plain array in a row missed
  every write to it, and the negative control proved nothing. The reader now dithers.

The 3-slot buffer and the FIFO queue across the cores wait for the Pico 2, whose
Cortex-M33 has exclusive accesses; `ThreeSlotCoresPico2` is written for the 3-slot
buffer (`roadmap.md`).

## Checks on the board

The CI runs everything under emulation; the board runs on the machine it is wired to,
which pulls rather than being pushed to. `tools/board_ci.sh`, started by a timer, fetches
`main` and, when it has moved, builds and runs seven checks on the Pico, then posts the
outcome as the commit status `board/pico`:

- `FourSlotCoresPico`, hard kernel: no read of the 4-slot buffer torn or going
  backwards in 10 s, and the plain array torn at least once;
- the same under the power-aware kernel, which changes speed under both cores;
- `TaskLEDPico` with the cost counters: its 1 ms round, 10 s of it, at most 5 µs on
  average;
- `TestTimerEventPico` under each kernel, through its trace (`tools/timer_events.py`):
  both outputs on their periods within 5 µs, high for 1 and 2 ms plus the path from the
  alarm to the task within 20 µs, and every event at most 2 µs after its alarm;
- `BenchDVFSPico` (`tools/dvfs_bench.py`): every change of speed and the wake-up path
  within a quarter over the means above, and the wake-up path shorter than the general
  one from the same speed, which is what it is for. `BenchVregPico` stays out: it takes
  the core below its specified voltage, which a check run on every commit should not.

Only `main` is ever built there, and only its owner pushes to it. A self-hosted runner
would have run pull requests too, forks' included, on a machine of the home network
with a probe on it — which a public repository cannot rule out by configuration alone.

The first run, on 2026-09-24 against 110b3cc: 321,760 reads, none torn, under each
kernel, the plain array torn 17,057 and 16,814 times; 10,069 rounds of 3.2 µs.

Installing it, under systemd on Linux or launchd on a Mac: `tools/board_ci.md`.

## Sources

- Raspberry Pi, [*RP2040 Datasheet*](https://datasheets.raspberrypi.com/rp2040/rp2040-datasheet.pdf):
  the timer and its alarms, `TIMER_DBGPAUSE`, the clocks, the PLL, the core
  regulator `VREG` and its voltages, the SIO, the boot from SRAM, the launch of core 1
  (section 2.8.2) and the power-on state machine (2.13), the watchdog.
- Raspberry Pi, [pico-sdk](https://github.com/raspberrypi/pico-sdk): the `no_flash`
  build type and the start-up sequence the port follows, and the reset of core 1
  before its launch (`multicore_reset_core1`).
- Arm, *ARMv6-M Architecture Reference Manual* and *Cortex-M0+ Technical Reference
  Manual*, on [developer.arm.com](https://developer.arm.com/documentation): the
  exceptions, `PRIMASK`, `WFI`, the NVIC, the ordering of memory accesses and `DMB`.
- [Renode](https://github.com/renode/renode) and the RP2040 models of
  [matgla/Renode_RP2040](https://github.com/matgla/Renode_RP2040), for the emulation
  (`emulation.md`).
