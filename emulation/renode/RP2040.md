# RP2040 emulation (Raspberry Pi Pico)

Renode has no RP2040 of its own. The models come from the community repository
[`matgla/Renode_RP2040`](https://github.com/matgla/Renode_RP2040). That repository
covers the timer and its four alarms, the clocks (PLL, XOSC, ROSC), the GPIO, the UART,
both cores, the SIO and the PIO. Its author has frozen it and moved on to the RP2350
(issue #21). The CI pins a commit (5aca847). The suite already runs on a fixed copy of
the timer (`Escapement_RP2040_Timer.cs`, below).

The first run of `TaskLEDPico` on these models lasted one second. It counted each
output's instances against those of GPIO 3:

| Output | Period | Instances | Measured ratio | Theoretical ratio |
|---|---:|---:|---:|---:|
| GPIO 25 (on-board LED) | 10 ms | 100 | 5.88 | 6.00 |
| GPIO 2 | 20 ms | 50 | 2.94 | 3.00 |
| GPIO 3 | 60 ms | 17 | 1.00 | 1.00 |

The processor ends up in the `wfi` of `IdleTask`. The board later measured the same
ratios.

## It does not work on macOS arm64

The repository is pinned to Renode 1.16.1, and its models have to be built against
Renode's assemblies. The `osx-arm64-portable` package is a self-contained binary that
exposes no DLL to reference. The “build from sources” mode fails too. It fails when the
platform is created, right after the ROSC initialisation: a peripheral constructor
throws, most likely that of `GPIOPort.RP2040Pads`.

These attempts failed on 2026-09-20:

- Renode 1.17.0 and 1.16.1;
- DLL mode and source mode;
- retargeting `netstandard2.1` to `net8.0`.

## A recipe that works, on Linux x86-64

The `linux-dotnet` package exposes its assemblies under `renode/bin/`. The build of the
models needs these assemblies. No root privileges are needed.

```sh
mkdir -p ~/escapement-rp2040 && cd ~/escapement-rp2040

# Renode 1.16.1, the version that runs on the .NET of the host
curl -fsSL -O https://github.com/renode/renode/releases/download/v1.16.1/renode-1.16.1.linux-dotnet.tar.gz
mkdir -p renode && tar -xzf renode-1.16.1.linux-dotnet.tar.gz -C renode --strip-components=1

# .NET installed in the user's home
curl -sSL https://dot.net/v1/dotnet-install.sh | bash -s -- --channel 10.0 --install-dir "$HOME/.dotnet"

# RP2040 models
git clone --depth 1 https://github.com/matgla/Renode_RP2040.git
cd Renode_RP2040/emulation
"$HOME/.dotnet/dotnet" build Peripherals.csproj -c Release \
    -p:RenodePath="$HOME/escapement-rp2040/renode/bin"
```

The original `netstandard2.1` target builds unmodified against 1.16.1. The clone takes
the repository's head. The CI checks out 5aca847 (`ci/Dockerfile`).

To run a firmware on the models:

```sh
export PATH="$HOME/.dotnet:$PATH"
~/escapement-rp2040/renode/renode --disable-xwt --console --plain \
  -e 'path add @'"$HOME"'/escapement-rp2040/Renode_RP2040;
      include @boards/initialize_raspberry_pico.resc;
      sysbus LoadELF @firmware.elf;
      start'
```

The recipe was verified on 2026-09-20: the bootrom runs 6,250,000 instructions in 0.05
emulated seconds, which is the nominal 125 MHz of the RP2040.

## In a container

On a machine without the package manager, such as Bazzite, the CI's image runs the suite
as it is, with the models built in it. `tools/soak_emulated.sh` starts the image under
podman (`ghcr.io/beber007/escapement-ci:3`).

## In CI

The `emulation-rp2040` job of `.github/workflows/build.yml` follows this recipe in the
image the CI runs in (`ci/Dockerfile`). In that image, Renode 1.16.1 and the models are
pinned and built once. The job links the models under `emulation/renode/rp2040`. It
builds the examples eleven times:

- the hard, the soft and the power-aware kernel, each under EDF and deadline-monotonic
  scheduling;
- the power-aware kernel undervolted;
- the power-aware kernel under its three other policies;
- the power-aware kernel with its idle task asleep at 12 MHz (`SLEEP_SPEED=0`, since
  2026-09-25).

The job runs `escapement_pico.robot` on each build. The suite learns which build it runs
on from `--variable KERNEL:PA`, `UNDERVOLT:1` and `POWER:...`:

| Test | What it proves |
|---|---|
| The probe task runs every millisecond | GPIO 4 is a 500 Hz square wave, 1 ms high and 1 ms low within 2 %: the 1 us tick of the timer, derived from the crystal, and the kernel scheduling on it |
| The three periodic tasks are scheduled | GPIO 25, 2 and 3 each rise and fall |
| The program of the README blinks the LED | `ReadmeExample`, built from the README's own text, hard kernel only: GPIO 25 toggles every 500 ms |
| The UART echo answers | `UARTEchoPico` sends back what it receives on UART0 |
| Two tasks send on the UART at once | `UARTSendersPico`: a task of 500 us preempting one that sends as fast as buffers come free, every line on UART0 whole over 0.3 s; before 2026-09-29, 60 lines of some 400 came out broken and the senders all but stopped (`method.md`) |
| Timer events wake the event-driven tasks | `TestTimerEventPico`: GPIO 2 high 1 ms every 5 ms and GPIO 3 high 2 ms every 10 ms, within 2 %: the kernel's alarms time the periods, the event manager on alarm 2 the high times, and each event-driven task runs when woken |
| Scheduling survives the 2^30 wrap of the kernel clock | `TaskWrapPico`, on a timer clocked at 1 GHz, crosses the boundary after 1.07 s: every task still runs afterwards and the 50 ms probe keeps its period within 2 % |
| Tasks preempt one another inside the FIFO queue and a slot buffer | `IPCPico`: over 50 ms, every record through the queue once and in order, no slot of the buffer read twice or torn, and some operations of the queue completed by the task that preempted them |
| Every part of the endurance test runs without error | `SoakPico` for 2.5 s, without the part between the cores: every part active and none in error |
| The endurance test drops optional instances, never a mandatory one | Soft builds only: `SoakFirmPico` for 2.5 s, its (2,5)-firm task's mandatory instances two of each five seen, some optional ones run and some dropped, none late |
| The power-aware kernel scales the frequency and the voltage | Power-aware builds only: over 100 ms, clk_sys never runs faster than the core voltage allows, the voltage changes at least 100 times (196 under OTE on 2026-09-22), reaches 1.05 V, or 0.90 V undervolted, and both 50 and 125 MHz are used; DRA keeps the fastest speed, 0 changes |

Every test runs on a fixed copy of the models' timer, `Escapement_RP2040_Timer.cs`,
which `escapement_pico_timer.repl` loads. The original lets its four alarms interfere
with one another: writing `INTR`, `INTF`, `INTE` or `ARMED` for one alarm acted on all
four. The original also compares an alarm with the whole 64-bit counter, where the chip
takes the lower 32 bits. The copy keeps a raw, a forced and an enabled bit per alarm, as
the datasheet describes. None of these defects has made a test fail yet, the timer
events included: those tests pass on the original too. The defects are fixed because the
event manager and the kernel now share the alarms and rely on those semantics. The copy
also makes the counter's frequency a property, which the wrap test raises to 1 GHz.

A platform description cannot redeclare a peripheral with another type. The tests
therefore unregister the original timer before they load the copy. The tests also spell
out the models' board script, since the copy can only be compiled once the models'
assembly is loaded.

`escapement_pico.repl` adds GPIO 2, 3 and 4 as LEDs to the models' board. It also adds a
model of the voltage regulator, which the models lack. That model is a Python peripheral
that keeps `VREG` and `BOD` and reports `ROK`. Write hooks on `VREG`, `CLK_SYS_CTRL` and
the post dividers of the PLL run `rp2040_dvfs_check.py`. That script keeps its counts in
scratch registers of the regulator model, for the test to read back.

The tests need two things that the recipe above does not:

- The firmware starts from SRAM. It is linked at 0x20000000 and started the way OpenOCD
  starts it on the board. The bootrom is loaded, then the ELF. Core 0's program counter
  is set to the first instruction of the image, which sets up its own stack.
- Core 1 is halted. The suite keeps core 1 in the bootrom, and `SoakPico` is told to
  skip its launch (`SoakLaunchCore1`). Left running under Renode, core 1 is a second
  time domain. Renode's LED tester then times some edges from the wrong core, as its
  source says. The probe failed a 2 % tolerance, although its edges were within 10 us.
  With core 1 halted, the edges measure 1000 us each, to within the 10 us of the
  sampling.

The probe test is not lax: told to expect durations 5 % off, it fails.
